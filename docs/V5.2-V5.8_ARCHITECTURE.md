# V5.2 – V5.8 架构说明

> **AI Multilingual Language Learning Platform（AI 多语种语言学习平台）**
> 技术栈保持不变：Flask / SQLAlchemy / SQLite / Docker / Gunicorn / Nginx（2vCPU-2GB 可承载）
> **未引入**：PostgreSQL / Redis / Elasticsearch / MongoDB / Kafka / Celery / PyTorch / TensorFlow / 大型 NLP 模型

---

## 1. 分层与目录约定

```
app.py                 create_app() 工厂：装配 + 幂等播种 + 增量列迁移
models.py              全部 ORM 模型（单一来源）
*_service.py           业务服务层（顶层模块，见下方 ⚠️）
routes/*.py            蓝图（控制器）：只做解析 / 调用服务 / 格式化响应
app/templates/         Jinja 模板
tests/test_v5*.py      按版本分片的测试
```

### ⚠️ 顶层 `services.py` 与 `services/` 包冲突

工程根目录**已经存在一个顶层 `services.py`**（Dashboard 统计等）。
若新建 `services/` 目录，会在 `import` 时把它**遮蔽**掉，导致整站崩溃。

> **规则：所有新增服务模块一律放顶层，命名 `*_service.py` 或平铺模块**
> （如 `mastery_service.py`、`ai_tutor.py`、`speaking.py`）。

## 2. 数据模型（V5 新增 / 演进）

| 模型 | 版本 | 职责 |
|---|---|---|
| `Course` / `Unit` / `Lesson` / `ContentItem` | V5.1–V5.4 | 课程体系；`ContentItem.kind` 覆盖 vocabulary / phrase / sentence / grammar / listening / reading / speaking / writing / quiz / review |
| `LexiconEntry` | V5.3 | 主词库；`production_ready` 判定 |
| `ReviewItem` | V5.0 起 | 抗遗忘队列 —— 「**何时复习**」的唯一真源 |
| `ContentMastery` | V5.5 起 | 掌握度 —— 「**掌握得多好**」的数据载体 |
| `QuizQuestion` / `UnitTestAttempt` / `UnitProgress` | V5.1 起 | 课时小测与单元测验 |

### ReviewItem 与 ContentMastery 的分工

```
复习「时间」→ ReviewItem.next_review_at（Leitner box 决定）   ← 单一真源
掌握「程度」→ ContentMastery.level（0-4，多源证据综合）
```

`mastery_service.record_practice()` 是**唯一写入口**：先走 Leitner，
再把 ReviewItem 的 `next_review_at` **搬运**到 ContentMastery。

> V5.5 曾两处各自计算间隔，随使用会缓慢分叉，出现「复习页显示到期、实际没安排」
> 的不一致。V5.6 已修正为搬运式单一真源。

## 3. 统一掌握度 Mastery 0-4

| level | 标签（EN） | 标签（ZH） | 判定要点 |
|---|---|---|---|
| 0 | New | 未学 | 无任何学习记录 |
| 1 | Learning | 学习中 | 有任意学习记录 |
| 2 | Familiar | 熟悉 | acc≥60 且 streak≥2 且 review≥2；或测验佐证 ≥60 |
| 3 | Strong | 扎实 | acc≥80 且 streak≥3 且 review≥3；或单元测试 ≥75 |
| 4 | Mastered | 已掌握 | 练习到位（acc≥90/streak≥5/review≥5）**且**测验佐证 ≥85 |

**关键语义**：`quiz_score` / `unit_test_score` 的 **0 表示「未测验」**，因此只作
**正向证据**抬高掌握度，绝不因低分倒扣；负向证据统一走 `wrong_count` / `weak`。

> 否则「没测过」会被误判成「测得很差」。

规则演进时用 `mastery_service.recompute(user_id)` 幂等重算。`overall` 只对**已测维度**求平均。

## 4. 外部依赖：Provider 适配器模式

三个能力各自 steroid 成三条通道，均为「**适配器 + mock 默认**」结构：

| 能力 | 模块 | 环境变量 | mock 默认行为 |
|---|---|---|---|
| AI Tutor | `ai_tutor.py` | `AI_PROVIDER` / `AI_API_KEY` / `AI_MODEL` | 本地规则（查站内数据） |
| 语音识别 STT | `speaking.py` | `SPEECH_PROVIDER` / `SPEECH_API_KEY` | **明确不可用** → 前端切手动输入 |
| 语音合成 TTS | `speaking.py` | 同上 | **明确不可用** → 前端改用浏览器内置朗读 |

所有 HTTP 走标准库 `urllib`，**不引入任何 SDK**，保持镜像轻量。

## 5. 🧪 Mock 标注清单（重要）

> 本项目遵循**诚实原则**：任何没有真实引擎支撑的能力，都必须在返回值与 UI 上
> 明确标注，绝不冒充 AI / 权威评分。

| 位置 | mock 开关 | 对外标注 |
|---|---|---|
| `ai_tutor.status()` | 无 `AI_API_KEY` | 返回 `"mock": true`；UI 显示「本地规则模式」 |
| `speaking.status()` | 无 `SPEECH_API_KEY` | `"practice_mode": true`；UI 显示「练习模式」 |
| `speaking.score()` | 同上 | `fluency` / `grammar` 返回 **`None`**（非 0） |
| STT | 同上 | `available: false` + 提示改用手动输入 |
| TTS | 同上 | `available: false` + `hint: browser-speech` |

### 为什么 `None` 而不是 `0`

`0` 会被读成「流利度极差」，而真相是「**没测**」。`None` 让前端显示「未评估」，
这才是诚实的表达。

## 6. 失败降级原则

**真实 provider 出错时必须显式失败，绝不悄悄退化成 mock 冒充成功回答。**

- AI Tutor：返回 `ok=false` + 「AI 服务暂时不可用」
- 掌握度写入（属派生数据）：整体包 `try`，失败**不影响**已算好的判分与单元解锁
  —— 用户不能因为次要写入失败就丢掉成绩

---

## 7. 安全边界

- API Key 只从环境变量读取，**绝不写入代码 / 日志 / 返回值 / Git**
- 入参：长度截断 + 控制字符清理 + **提示注入剥离**（`ignore previous instructions` 等）
- `system prompt` 由服务端固定，用户文本**只进 user 角色**
- 请求带超时；异常信息不回显 `Authorization`
- 文件名路径穿越校验（`../../` 一律拒绝）
- 未登录统一返回 **401 JSON**（非 302），便于前端区分处理

### ⚠️ 测试隔离约定

`config.Config.DATABASE_URL` 是**类属性**，在 `config` 模块首次 import 时就固化。
因此**不要**用 `os.environ["DATABASE_URL"]` 选临时库 —— 若先收集了会 import config
的其他测试模块，临时库会被静默忽略，`create_app()` 会连到真实库。

> 正确做法：显式定义 config 子类，如 `class _V56Config(DevelopmentConfig): DATABASE_URL = ...`

## 9. 增量列迁移（`schema_compat.py`）

`db.create_all()` 不会给**已存在**的表补列。新增列必须同时登记到
`schema_compat._EXTRA_COLUMNS`，否则老库（含生产）会直接报错。

> 教训：`notify_email` 曾漏登记，导致任何 `SELECT users` 都报
> `no such column: users.notify_email`。该问题单独跑测试发现不了，
> 只在「测试连到真实老库」时才暴露。
