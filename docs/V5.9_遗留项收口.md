## 一、每日配额（Daily Quota）

### 问题

V5.7 / V5.8 只做了**套餐门禁**：AI Tutor 与 Speaking 非 PRO 一律 403。
这带来两个后果：

- 免费用户**完全无法体验**核心卖点，转化链路断了；
- 付费功能没有任何滥用防护上限，一旦 key 配置上去就是敞口。

### 设计：套餐门 + 配额门，两张表而不是一张

```
                        ┌─ 命中 FEATURE_PLANS（PRO）──→ 放行，不限量
check(feature, user) ───┤
                        └─ 未命中 ──→ 查 DAILY_TRIAL_QUOTAS ──→ 有余额则放行
                                                              └→ 无余额则 403 quota_exceeded
```

分成两张表而不是把 `free` 塞进 `FEATURE_PLANS`，是为了让原规格
「**AI 与 Speaking = PRO**」保持字面成立：

- `allowed_plans("ai_tutor")` 仍然只返回 `("pro",)` —— 测试与文档都不用改；
- 低档用户拿到的是**临时试用**（`by_quota=True`），不是「获得授权」；
- UI 据此显示「今日试用还剩 N 次」，而不是「已解锁」。

### 默认值

| 功能 | free | premium | pro |
|---|---|---|---|
| `ai_tutor` | 3 次/天 | 20 次/天 | 不限量 |
| `speaking` | 5 次/天 | 30 次/天 | 不限量 |

可用环境变量覆盖（无需改代码）：`TRIAL_QUOTA_<FEATURE>_<PLAN>`，
例：`TRIAL_QUOTA_AI_TUTOR_FREE=10`。非法值（非数字 / 负数）忽略并保留默认值 ——
**绝不因为一个笔误把功能直接关掉**（`0` 是合法值，表示「不给试用」）。

### 三个容易做错的细节

**1. 只在成功路径计数。**
计数写在视图函数返回前，而不是 `before_request`。否则参数错误（422）
也会吃掉用户额度 —— 用户会因为「打错一次字」白白少一次机会。

**2. 纯查询端点不计数。**
`/api/speaking/status`、`/api/speaking/listening`、`/api/ai-tutor/status`
都不消耗额度。否则刷新页面就在烧次数。

**3. 日期口径用 UTC 自然日。**
用服务器本地时间会让「今天」的长度随部署地漂移，用户会遇到
「明明说是每天重置，怎么刚到下午就没了」。

### 数据模型

```python
class UsageCounter(db.Model):
    __tablename__ = "usage_counters"
    # 唯一约束保证「一天一行」，计数不会被悄悄分散到多行
    UniqueConstraint("user_id", "feature", "day", name="uq_usage_user_feature_day")
```

| 字段 | 说明 |
|---|---|
| `user_id` / `feature` / `day` | 联合唯一；`day` 为 UTC `YYYY-MM-DD` |
| `count` | 当日累计成功次数 |

### 失败策略：宁可少收钱，不能砸服务

配额是**旁路**。计数表不可读时按「已用 0」放行，计数自增失败时忽略。
已付费用户绝不能因为一个旁路故障就用不了已付费功能。

### 已知取舍

计数自增是「读-改-写」三步，多进程并发下会**少计**（不会多计）。
当前部署规模（2vCPU / Gunicorn 单 worker）精度足够；将来横向扩展时，
改成 `UPDATE ... SET count = count + 1` 的原子语句即可，接口不变。

### 清理

`usage_counters` 会随时间膨胀（用户数 × 功能数 × 天数），
由 `flask purge-usage --days 90` 清理 90 天前的行，建议挂月度定时任务。

## 二、录音降级与麦克风释放

### 问题

原实现只有一层判断：`if (navigator.mediaDevices && window.MediaRecorder)`。
不满足时禁用按钮 —— 看起来处理了，实际漏了三件事：

1. **没接 STT 引擎时录音按钮照样可用**。用户录了 10 秒，上传后收到
   「未配置语音识别引擎，请手动输入」——白忙一场。
2. **麦克风从不释放**。`getUserMedia` 拿到的 stream 没有 `stop()`，
   标签页会一直显示「正在使用麦克风」，直到关掉页面。这是隐私与资源问题。
3. **失败后按钮卡死**。用户拒绝授权时 `catch` 里只改了文案，没恢复按钮状态，
   之后再也点不动。连点「录音」还会叠出多个 `MediaRecorder` 互相覆盖。

### 修复

```
canRecord = MediaRecorder 可用
            && 站点接了 STT 引擎          ← 新增
            && getUserMedia 可用
```

- 任一不满足 → 禁用按钮 + 说明**具体原因**（是浏览器不支持，还是没接引擎）；
- `releaseMic()`：停止时、失败时、以及 `pagehide`（用户直接跳转）时关闭所有 track；
- `recording` 标志防连点；`catch` 分支恢复按钮状态。

手动输入路径全程保留 —— 没有识别引擎时用户照样能练，只是得自己打字。

## 三、`recompute-mastery` 运维入口

### 问题

V5.6 提供了 `mastery_service.recompute(user_id)` 函数，但**只有 Python 函数**。
掌握度规则从 V5.5 演进到 V5.6 后，老数据仍是按旧规则算出的 level，
部署到服务器后运维无从下手 —— 要么临时写脚本，要么直接改库。

### 修复

```bash
flask recompute-mastery                  # 全量重算
flask recompute-mastery --user-id 42     # 只重算指定用户
```

- **幂等**：只在 level 真的变化时才写库，第二次执行输出「更新 0 行」；
- 已在 `tests/test_v59_ops_cli.py` 中锁定「第二次必须是 0 行」，
  否则说明规则判定不稳定。

**首次部署后执行一次即可**（把 V5.5 规则产出的老行刷平）。

## 四、听力卡片的两个缺陷

这两个都是**服务层单测全绿也照样漏**的问题，只有渲染页面才能发现。

### 4.1 DOM id 冲突

```jinja
{# 修复前 #}
<div id="lm-{{ item.content_id }}">
```

听力素材来自 legacy `Word`（没有 `content_id`），于是所有卡片共用
`id="lm-"`。点任意一张卡的「显示答案」，`getElementById` 只会翻开第一张。

**修复**：`listening_items()` 返回 `"id": f"w{word_id}"`，模板改用 `item.id`。
测试逐条断言 id 唯一（`tests/test_v59_pages.py`）。

### 4.2 答案先泄露

```jinja
{# 修复前 #}
<div class="listen-surface">{{ item.surface }}</div>   ← 一上来就显示单词
```

先看到单词就不叫听力练习了。

**修复**：答案区默认 `hidden`，Reveal 后显示 `surface` + 音标；
中文释义只在非英文界面给出（**英文界面不输出中文**是项目既有约定）。
